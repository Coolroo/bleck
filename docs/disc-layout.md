WBFS is ~408 MiB rather than 4.5 GiB. The us0 dump was already scrubbed; the eu0
ISO produced by `dolphin-tool` is full-size (4.7 GB on disk) but only 492 MiB is
real.

`cert.bin`, `h3.bin`, and — usefully — an **`align-files.txt`** and `setup.sh`
generated by WIT to support faithful rebuilds.

## Formats identified

### TPL — textures ✅

Magic `00 20 AF 30` — **standard Nintendo TPL**. Confirmed on both `spmario.tpl`
and the extensionless `a/p_wii_mario-`.

**This is the finding that closes research open-question #1.** SPM does not use a
bespoke texture format. Existing Wii tooling reads TPL directly, so texture work
is an *integration* task, not a reverse-engineering one.

### `/a` — paired model + texture files ✅ (pairing) 🔶 (semantics)

Files in `/a` come in pairs: `name` and `name-`.

| File | Size | First bytes |
|---|---|---|
| `a/p_wii_mario` | 291,528 | `00 01 5F 5C` then the ASCII string `p_wii_mario` |
| `a/p_wii_mario-` | 1,366,048 | `00 20 AF 30` — **TPL** |

✅ **Verified:** the `-` suffixed member of each pair is a TPL texture bank.

🔶 **Hypothesis:** the non-suffixed member is the model/animation data, carrying
an embedded name string near the header. Consistent with the sizes (textures
dominate) and with Paper Mario conventions generally, but the container format
itself is not yet identified.

### `map/*.bin` — LZ77-compressed U8 archives ✅ **SOLVED**

383 files (eu0), named `aa1_01.bin`, `aa1_02.bin`, `aa2_01.bin`… **All 383 are
LZ77-headed**, and every one decompresses to a **Nintendo U8 archive**
(magic `55 AA 38 2D`).

So the container stack is: `LZ77 → U8 → member files`. Both layers are standard
Nintendo formats — again, no bespoke reverse engineering needed.
[`tools/u8.py`](../tools/u8.py) reads *and writes* them (and transparently
un-LZ77s on read).

✅ **Repacking is bit-exact.** `tools/verify_roundtrip.py` confirms all **383/383**
eu0 map archives survive unpack→repack byte-identically.

**U8 layout as SPM uses it** (measured, not assumed):

- File data aligned to **32 bytes**; archives packed contiguously with alignment
  padding only, and **no trailing padding**
- `rootNodeOffset` = `0x20`, `dataOffset` = `align32(0x20 + headerSize)`
- `headerSize` = node table + string table
- **Node order is a flat depth-first listing and must be preserved** to repack
  identically

`map/aa1_01.bin` — 424,712 B on disc, 1,131,524 B decompressed, 7 files:

| Member | Size | Format |
|---|---:|---|
| `./dvd/map/aa1_01/map.dat` | 561,630 | first u32 = its own size |
| `./dvd/map/aa1_01/texture.tpl` | 188,576 | TPL |
| `./dvd/map/aa1_01/camera_road.bin` | 936 | contains string `SPMario_` |
| `./dvd/bg/aa1_01_00.tpl` | 122,944 | TPL (background) |
| `./dvd/bg/aa1_01_02.tpl` | 122,944 | TPL |
| `./dvd/bg/aa1_01_04.tpl` | 122,944 | TPL |
| `./dvd/setup/aa1_01.dat` | 11,204 | setup file |

✅ **Developer paths are preserved.** Members are stored under `./dvd/…`, i.e.
the original build tree. Useful for inferring intent and for matching against the
REL's embedded source filenames (`aa2_02.c` ↔ `map/aa2_02.bin`).

✅ **No evt bytecode found inside the archives.** Combined with the research
finding that evt scripts live in the DOL/REL, and with `aa1_01_init_evt` being a
*memory address* in spm-docs, this refines the earlier hypothesis: **map archives
hold assets; map scripts and code live in the REL.**

### ⚠️ Setup files exist in two places — byte-identical ✅

`files/setup/aa1_01.dat` and the `./dvd/setup/aa1_01.dat` *inside*
`map/aa1_01.bin` are the **same 11,204 bytes** (matching SHA-256). Of the first
40 map archives, **17 embed a setup file and 23 do not.**

**This is a modding trap.** Editing one copy while the game loads the other
produces a silent no-op — the most annoying class of bug to diagnose.

🔶 **Unresolved and important: which copy does the game actually read?** Answer
this before building any setup-file editing feature.

**Correction to an earlier note in this doc:** setup files are *not* a uniform
11,204 bytes. That was drawn from a six-file sample. Across all 227 files in
`files/setup/` there are **17 distinct sizes** — 184 are 11,204 B, but they range
from 2,804 to 11,980 B. Do not assume a fixed-size record layout.

### `rel/*.bin` — LZ77-compressed ✅ **CONFIRMED**

Every REL across **both** regions begins with byte `0x10` — the Nintendo LZ77
type-0x10 marker — followed by a 24-bit little-endian uncompressed size:

| File | On disc | Magic | Size field | Ratio |
|---|---:|---|---:|---:|
| `eu0/rel.bin` | 934,593 | `10401e32` | 3,284,544 | 3.51× |
| `eu0/relD.bin` | 970,808 | `10606c33` | 3,370,080 | 3.47× |
| `eu0/relF.bin` | 927,026 | `1008eb31` | 3,271,432 | 3.53× |
| `us0/rel.bin` | 940,113 | `10503832` | 3,291,216 | 3.50× |
| `us0/relF.bin` | 924,194 | `10e8bd31` | 3,259,880 | 3.53× |

✅ **Verified by decompression.** [`tools/lz77.py`](../tools/lz77.py) decompresses
all five to *exactly* their declared sizes, with no trailing slop and no
malformed back-references.

The output is a valid **Nintendo REL v3** in every case:

| File | Module ID | Sections | `secInfoOff` | Version |
|---|---:|---:|---|---:|
| `eu0/rel.bin` | 1 | 19 | `0x4c` | 3 |
| `eu0/relD.bin` | 1 | 23 | `0x4c` | 3 |
| `eu0/relF.bin` | 1 | 18 | `0x4c` | 3 |
| `us0/rel.bin` | 1 | 19 | `0x4c` | 3 |

`sectionInfoOffset = 0x4C` is the standard REL v3 header size, and section tables
parse cleanly. This is conclusive — not an inference.

**Format:** 4-byte header (`0x10` marker + 24-bit LE uncompressed size), then
blocks of one flag byte + 8 units, MSB first. Clear bit = literal byte; set bit =
back-reference over two big-endian bytes, 4-bit `(length - 3)` and 12-bit
`(displacement - 1)`. Overlapping copies occur and must be handled byte-by-byte.

### `rel.bin` / `relD.bin` / `relF.bin` — three builds of one module ✅🔶

All three carry **module ID 1** — they are alternative builds of the *same*
module, not different modules loaded together.

⛔ **Ruled out:** D = Deutsch / F = French. The US disc carries neither language
yet ships `relF.bin`.

✅ **`relD` is a debug build.** Evidence:

- Contains the string **`Debug:Stage Skip ON`** — absent from both others
- Retains **34** distinct embedded source filenames vs **21** in the others; the
  13 extras include `relocatable_module.c` and the SDK's `GXGeometry.h`, the
  signature of an assert-enabled build
- 23 sections vs 18–19; largest of the three (3,370,080 B decompressed)
- Debug-format strings such as `0x%08x:   0x%08x    0x%08x`, `(index:%d)`,
  `KouraMaxSet ... Stage:%d`

🔶 **`rel` vs `relF` remains unresolved.** Their string sets are **99.8%
identical** and they differ by a single section (19 vs 18). Whatever distinguishes
them is subtle — plausibly a build flag rather than a content difference. Not
worth guessing at.

**This means a PAL disc ships a debug build of the main module.** That is
potentially valuable for reverse engineering: `relD` names 13 source files the
retail builds omit.

### `a/ag2tg.bin` — named archive/index 🔶

Begins with the ASCII string `EFF_Baketu` followed by null padding — the shape of
a name table or archive directory. Not investigated further.

## us0 vs eu0 — tree comparison ✅

Diffing the two extracted file lists: **82 differences, all additions in eu0.
There are zero US-only files — `eu0` is a strict superset of `us0`.**

This is a meaningful result for the project: developing against eu0 costs nothing
in content coverage. Every asset present in the US build exists in the PAL build.

PAL-exclusive content, excluding the obvious EU localization
(`FR`/`GE`/`IT`/`SP`/`UK` message and UI files):

| Path | Note |
|---|---|
| `map/go1_03.bin` | **A map that does not exist in the US build** (21,355 B) |
| `rel/relD.bin` | A third REL variant (970,808 B) |
| `msg/JP/*.txt` | **Japanese text — 11 files — shipped on the European disc** |

The `map/go1_03.bin` and `msg/JP/` findings are the interesting ones. `go1_01`
and `go1_02` are byte-identical in size across regions (12,864 / 14,322), so
`go1_03` is a genuine PAL addition rather than a renumbering.

🔶 Unexplained: why a PAL release carries a full Japanese message set.

## What this means for the toolkit

1. **Textures are solved-adjacent.** TPL is standard; wire up existing tooling
   rather than reversing anything.
2. **`map/*.bin` is the high-value target.** It plausibly unifies level data and
   evt scripts, and it connects directly to the one live script tool
   (evt-disassembler).
3. **`setup/` is skawo's territory.** Check what that editor already covers before
   duplicating it — research open-question #2.
4. **Compression may gate REL work.** Confirm the LZ77 hypothesis early; it's a
   small experiment with a large blast radius.
